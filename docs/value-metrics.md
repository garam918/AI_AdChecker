# 평가 지표와 실제 가치 검증

“기존 검수 30분 → ContentLint 30초”는 아직 입증된 성과가 아닙니다. 화면에서 가정 기준선과 절감 배수를 제거했습니다. 서버 처리 시간, 사람의 검토 완료 시간, 판단 품질을 구분합니다.

## 자동 처리 지표

| 필드                         | 의미                                                                   |
| ---------------------------- | ---------------------------------------------------------------------- |
| `metrics.elapsedMs`          | 서버 분석 작업 소요 시간. 사용자 읽기·수정 시간과 네트워크 전체가 아님 |
| `metrics.mode`               | 최종 AI 위험 해석 완료 `live` / 최종 규칙 대체 `offline`               |
| `metrics.attempts`           | 단계별 제공자·모델·성공/실패·시간. OCR만 성공한 부분 분석도 보존       |
| `metrics.fallbackConfigured` | 대체 제공자 설정 존재 여부. 실제 인증·잔액 확인이 아님                 |
| `metrics.aiBudgetMs`         | 요청별 AI 클라이언트의 공유 시간 예산. 전체 HTTP 지연 보장이 아님      |

## 검토 작업 기록

결과 화면의 ‘이번 검토 종료 · 시간 기록’은 **첫 분석 요청부터 종료 버튼까지** 경과 시간을 기록합니다. 대기·읽기·수정·재검사가 포함되며, 첫 입력 전에 자료를 준비하거나 문구를 입력한 시간은 포함하지 않습니다. 분석한 원문과 수정 초안이 다르면 재검사 전에는 종료할 수 없습니다.

- 초안을 다시 바꾸면 완료 표시를 해제합니다. 저장 기록을 다시 열어 둔 며칠을 새 검토 시간에 합산하지 않습니다.
- 메모에 오탐 의심·누락·남은 증빙을 기록할 수 있습니다. 이 값은 전문가 판정이나 실제 사용자 연구를 대신하지 않습니다.
- 저장 버튼을 눌렀을 때만 이 브라우저의 `localStorage`에 원문·결과·초안·메모·시간을 보관합니다. 최대 10개, 다른 기기 동기화 없음, 이미지 원본 제외. 공용 PC 저장을 주의하고 삭제하면 복구할 수 없습니다.
- 개발자가 화면 동작을 확인하며 기록한 시간은 실제 고객의 시간 절감 근거로 사용하지 않습니다.

## 두 평가 데이터셋

- `evals/end-to-end/cases.json`: 기존 40개 회귀 사례, FLAG 27 / SAFE 13. 기존 구현 분야를 보존한 회귀셋이며 규칙 설계와 겹칩니다.
- `evals/challenge/cases.json`: 새 내부 합성 40개, 일반 광고·일반 식품 각각 FLAG 12 / SAFE 8. 부정문·암시·상충 주장 중심이며 **독립적 전문가 정답셋이 아닙니다**.

```sh
npm run eval:e2e -- --dataset=regression --strict
npm run eval:e2e -- --dataset=challenge
npm run eval:e2e -- --dataset=challenge --live
npm run ai:eval -- --live --text-repeats=5
```

실제 AI 호출은 과금됩니다. 모드·실행 시각·고유 ID별 `outputs/evaluations/` 파일을 생성하고 실행 중 체크포인트를 보존합니다. JSON의 `completed`, `expectedCases`, 실제 사례 수, 데이터 SHA-256을 확인하세요. 미완료 결과를 전체 성적으로 발표하지 않습니다. `--strict`는 미탐·오탐·오류 시 실패합니다. 이전 `--baseline-minutes` 옵션은 과거 파일 호환용 가정값일 뿐, 절감 배수를 산출하지 않습니다.

### 자동 지표의 정의와 한계

- 결과 반환율: 오류 없이 결과가 반환된 사례 / 전체. 규칙 대체를 포함합니다.
- 최종 AI 완료율: `mode=live` 사례 / 전체. 준비 단계만 성공한 경우는 제외합니다.
- 탐지 성공률: FLAG 중 기대 이슈 유형을 **모두** 찾은 사례 / 전체 FLAG. 일부 유형만 맞힌 경우도 미탐 목록에 남깁니다. 유형 라벨 차이와 실제 의미 누락은 결과 원문으로 추가 검토해야 합니다.
- 출처 연결률: 탐지 성공한 FLAG에서 일치하는 이슈 모두가 검증된 조항 ID를 가진 비율. **출처 관련성이나 법적 해석 정확도가 아닙니다.**
- 오탐률: 결과가 반환된 SAFE 중 이슈가 생긴 비율. SAFE 오류는 분모에서 제외하고 실패로 별도 표시합니다.
- 핵심 항목: 전체 이슈 수와 구분해 `keyIssueIds`가 1~3개인 비율을 계산합니다. 이슈 없는 SAFE는 이 분모에서 제외합니다.
- 지연: 반환된 결과의 중앙값·p95. 규칙 대체가 빨랐다고 AI가 빨랐다고 주장하지 않습니다.

동일한 데이터 해시의 규칙·AI 실행을 비교하고, `analysis`에 보존한 원문·이슈·수정안·출처와 `humanReview: PENDING`을 별도 검토합니다. AI가 연결된 출처를 실제로 적절하게 사용했는지, 새로운 사실을 만들어 냈는지, 정상 표현을 불필요하게 지적했는지는 사람의 평가가 필요합니다. 도전 사례를 보고 로직을 조정했다면 이후 결과는 개발/회귀 성적이며 새로운 홀드아웃이 필요합니다.

## 실제 사용자 비교 실험 절차 (아직 미실시)

1. 마케터·검수 경험자 5명 이상을 모집하고 익명 참가자 ID와 경험 수준을 기록합니다. 외부에 공개할 수 있는 합성/허가받은 문구만 사용합니다.
2. 난이도가 비슷한 A/B 세트(각 6개: FLAG 4, SAFE 2)를 준비합니다. 동일 문구를 두 번 보면 학습 효과가 있으므로 서로 다른 대응 문구를 배정합니다.
3. 참가자별로 수동→도구 / 도구→수동 순서를 번갈아 배정합니다. A/B 세트도 교차 배정합니다. 평가자는 조건을 가리고 결과물을 검토합니다.
4. 두 조건 모두 자료 제시부터 최종 위험 표현·근거·수정안 제출까지 외부 타이머로 측정합니다. 앱 내부 시간은 첫 분석 요청 이후만 포함하므로 보조 지표로 사용합니다. 중단·실패·휴식 기준을 사전에 고정합니다.
5. 누락, 오탐, 출처 관련성, 새 사실 생성, 수정 후 잔여 문제를 동일 기준으로 평가합니다. 품질 하락을 감춘 속도 개선은 성과로 주장하지 않습니다.
6. 참가자 수·완료율·조건별 중앙값·참가자별 차이와 품질을 함께 공개합니다. 작은 표본을 모집단 효과로 일반화하지 않습니다.

개별 관측 기록 예시(빈 값은 미측정이며 임의로 채우지 않음):

```json
{
  "participantId": "P01",
  "experience": null,
  "taskId": "A01",
  "condition": "CONTENTLINT",
  "sequence": 1,
  "externalElapsedSeconds": null,
  "appReviewElapsedSeconds": null,
  "completed": null,
  "misses": null,
  "falsePositives": null,
  "sourceRelevance": null,
  "rewriteAddedUnsupportedFacts": null,
  "reviewerId": null,
  "notes": null
}
```

측정 전 발표 문구는 “검토·수정·재검사의 시간을 기록할 수 있는 사전검수 도구” 수준으로 제한합니다. 실제 비교 실험이 끝난 뒤에만 관측된 값을 근거와 함께 사용합니다.
